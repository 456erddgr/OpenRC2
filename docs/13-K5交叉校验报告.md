# 13 · K5 交叉校验报告（Java 混控 ↔ 原生核心）

复现：`adb shell am start -n com.rc2.etx/.MainActivity --es action crosscheck`
→ 报告落在 `/sdcard/Android/data/com.rc2.etx/files/crosscheck.txt`（0.8.2 起）。
实现：`app/src/com/rc2/etx/jni/CrossCheck.java`（116 行）；每次跑 9 组输入向量 + 4 轴各 5 点扫描。

## 结论 1（已修）：轴序必须按 LH,LV,RV,RH 传

原生核心按 EdgeTX 语义吃 `axes[0..3] = LH, LV, RV, RH`。RC2 的物理轴（App 内部命名，已由用户确认）是：

| App 变量 | 含义 | 对应 EdgeTX 轴 |
| --- | --- | --- |
| `lx` | 偏航（左摇杆水平） | LH |
| `ly` | 油门（左摇杆竖直） | LV |
| `ry` | 俯仰（右摇杆竖直） | RV |
| `rx` | 横滚（右摇杆水平） | RH |

早先我按 `lx,ly,rx,ry` 顺序传，等于把 **RV/RH 互换**（俯仰↔横滚会对调）。0.8.3/0.8.4 已改成 `lx,ly,ry,rx`，
交叉校验复测：`rx` 只动 ch4（RH）、`ry` 只动 ch3（RV）、`lx` 只动 ch1、`ly` 只动 ch2，**四轴互不串**。

## 结论 2（待上游改）：`etx_channels_us` 的口径不是 CRSF

原生核心当前输出 **1500 ± 512**（满行程 988 / 2012），而 CRSF 口径是 **992 ± 819**（172 / 1811）。
两者中心差 508、半幅差 307，直接拿去组 CRSF 帧会一开始就把通道顶到边界外。

要求（写进 `docs/07` 契约）：`us = 992 + ch * (819/1024)`，其中 `ch` 是 EdgeTX 内部 -1024..1024；
在 172 / 1811 处夹住。验收：轴满行程时 `us=172 / 1811`，中位 `992`。

## 结论 3：四轴跨度一致、无越界（原生自身口径下）

| 轴 | min | max | 跨度 |
| --- | --- | --- | --- |
| LH(ch1) | 988 | 2001 | 1013 |
| LV(ch2) | 988 | 2012 | 1024 |
| RV(ch3) | 988 | 2012 | 1024 |
| RH(ch4) | 988 | 2012 | 1024 |

LH 上界 2001 比其余 2012 少 11，是 11bit 取整（`1024+660=1684` → 换算后 2001.x）造成，不是 bug。

## 更正（0.9.0 实测，覆盖本文上面"结论 1"）

**`etx_set_inputs` 的轴序是 MCU 物理序 `RH, RV, LV, LH`（= 摇杆通道 ch0..ch3），不是 `LH,LV,RV,RH`。**

甄别方法（A/B 两组）：
- A 组：按 `LH,LV,RV,RH` 传 `mid + u*span` 的原始值 → 端点只到 82%（如 321 而不是 173）。
- B 组：四轴都传 1024 → 输出 `967 / 1121 / 923 / 953`；拿 `radio.yml` 反推中心，只有
  `RH(1044/624)→953`、`RV(929/554)→1121`、`LV(1075/600)→923`、`LH(1055/642)→967` 能对上
  → ch1←RH、ch2←RV、ch3←LV、ch4←LH。
- 按 B 的推论传真机 `raw[0..3]`（正好是 RH,RV,LV,LH）后：

| 轴 | min | max | 跨度 |
| --- | --- | --- | --- |
| lx(RUD)→ch4 | 173 | 1811 | 1638 |
| ly(THR)→ch3 | 173 | 1811 | 1638 |
| rx(AIL)→ch1 | 173 | 1811 | 1638 |
| ry(ELE)→ch2 | 173 | 1811 | 1638 |

与 Java 侧 AETR 输出逐通道差 **≤1us**（172/173、1811/1811、中位 992/992）→ **K5 实质通过**。
入参口径：**原始 11bit ADC（0..2047）**，校准由核心按 `radio.yml` 自己做。

## Java 侧同步改动（0.8.5–0.9.0）

- 新增 `app/src/com/rc2/etx/radio/RadioYml.java`（122 行）：解析 `RADIO/radio.yml` 的 `semver/board/stickMode` 与 7 轴 `mid/spanNeg/spanPos`。
  真机验证输出与 V15 完全一致：`LH 1055/642/608  LV 1075/600/546  RV 929/554/598  RH 1044/624/653  P1 1010/995/1010  P2 1029/1003/1003  P3 1024/1024/990`。
- `DumlStick.setAxisSpans(mid,neg,pos)`：摇杆归一化不再用统一 ±660，改按每轴 `spanNeg/spanPos`（解决"一侧先到顶、另一侧到不了顶"）。
- MCU 通道 → `radio.yml` 轴序：`ch0=RH ch1=RV ch2=LV ch3=LH ch4=P1 ch5=P2`。
- `Radio.fillNativeAxes()`：有真机摇杆时直传 `duml.raw[]`；没有时用 `radio.yml` 的 mid/span 反算出等效 ADC（`synthNativeAxes()`），保证两条路径同口径。

## 更正与最终结论（1.9.5，2026-11-01）
此前"跨度=0"的失败是**测试口径错**，不是核心错：交叉校验用了 4 轴 legacy 通道，而 so 端该分支内部还会再做一次轴序置换，与我们已按 MCU 物理序输出的数据二次互换。改走 7 轴生产路径后：
- 9 组向量：原生 vs Java 混控逐通道差 **≤1us**；
- 四轴扫描：`min=173 max=1811 跨度=1638`，端点未越界。
**K5 通过。**
