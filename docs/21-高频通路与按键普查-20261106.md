# 21 · 高频通路与按键普查（2026-11-06）

> 现场：RC2（`6UZBM6L02104CA`，Android 11）已连。目标是找「比 40007 的 10Hz 更快」的数据通路，
> 以及「后面两个自定义键 + 前面拍照/录像键 + 拨轮切档」在哪里能拿到。

---

## 一、结论先说

| 问题 | 结论 | 证据强度 |
|---|---|---|
| 有比 10Hz 更快的通路上吗？ | **有，但给的是死值。** binder `transact(4)` 实测稳定 **60Hz** 回包 | 实测（`stat pollHz=60 replyHz=59`） |
| 那个高频通路能拿到真摇杆吗？ | **不能。** 60Hz 回包里 6 个通道恒为 `1024,1024,1024,1024,1024,1024`，一次都没变过 | 实测（连续采样 30 分钟，`changeHz=0`） |
| 40009 那条呢？ | 也是**死值**。独占 30 秒收 10 帧（≈0.33Hz），全是同样的 1024 占位 | 实测 |
| 真摇杆值在哪？ | **只有 `40007`**，`cmd_set=6 / cmd_id=174`，实测 `stickHz=9~10` | 实测 |
| 后面两个自定义键在哪？ | 40007 的 `06/AE` 帧里，**载荷偏移 16 之后那 12 字节之外的标志位**里；本机这台**未观察到按键变化帧** | 部分 |
| 前面拍照/录像键？ | 同上，`06/174` 帧的 `p0` 位域（快门/录像/返航），但**本机 40007 从没出现过非零 p0** | 未确认 |
| 拨轮切档？ | 40007 的 `06/AE` 第 4/5 个 u16（我们已经在读，就是 `raw[4]/raw[5]`） | 已实现 |

**一句话**：别人的 "22Hz" 大概率**不是 40007**，而是把 binder 的 60Hz 回包做了插值/平滑，
或者用了我们还没打到的那条订阅式推送。**单纯提轮询频率拿不到真值** —— 这一点我已经用 `changeHz=0` 证死了。

## 二、实测过程与原始数据

### 2.1 端口普查（`/proc/net/tcp` 里所有 LISTEN）

| 端口 | 归属进程 | 独占 20 秒收到的字节 | 内容 |
|---|---|---|---|
| `40007` | `dji_link` (pid 1236) | 0 ~ 176 B（不稳，见 §2.2） | DUML，`06/AE` 摇杆帧 = **真值** |
| `40008` | `dji_link` | **0** | 只监听不推 |
| `40009` | `dji_link` | 405 ~ 678 B / 30s | DUML，`06/AE` 但**全是 1024**（seq 每次 +2，说明中间丢帧） |
| `8901` | `dji_link` | 0 | 只监听不推 |
| `8902` | `dji_sdrs_agent` (pid 1251) | **1.49 MB / 20s（≈74 KB/s）** | 图传/遥测私有流，**不是** DUML，结构自描述，无 1024 摇杆字段 |
| `5744` | `gnss@1.0-service` | 0 | GNSS，无关 |

`8902` 是全场唯一真正的高频流（**593 包/秒**），但包结构是这个样子（82 字节那类）：

```
0002 0000 0000 00 | aa aa 14 10 | f6 64 4e 00 | db 2b 0b 00 ...
```

里面固定的 `0x0400`(=1024) 出现在 [20]、[40]、[52] 三处 —— 属于**协议常量**（分辨率/帧率/通道数之类），
不是摇杆采样值。且 `dji_sdrs_agent` 是图传服务，不是遥控输入服务。

**所以 8902 这条路排除。** 高频 ≠ 有摇杆。

### 2.2 `40007` 是被动订阅式的（关键行为）

实测三次对照：

```
A. app 没跑，nc 连 40007 15 秒   → 176 B
B. app 跑着，nc 连 40007 15 秒   →  38 B
C. app 跑着，nc 连 40009 15 秒   → 512 B
```

`B` 比 `A` 少 —— 说明 `dji_link` 对本地客户端**做了配额/抢占**：谁先连谁拿，后来者只能分到残羹。

还有一次更极端：`am force-stop com.rc2.etx` 后独占 60 秒，收到 **0 字节**。
原因是 `dji.go.v5`（uid 10030）还占着这条连接（`ss` 里能看到 `127.0.0.1:40007` 的一条 ESTAB）。
停掉 `dji.go.v5` 之后仍然是 0 —— 说明断开后 `dji_link` 需要一个"重新订阅"的动作才会继续推，
而**这个动作我们还没找到**（可能是另一个 binder 调用）。

> 这解释了历史遗留问题：「40007 每 3~6 秒 RST 一次」。它不是网络抖动，
> 而是配额用尽被踢；重连后能拿到几帧，然后再被踢。

### 2.3 binder 的 60Hz：真高频，但值是死的

`RcProService` 在 `com.dpad.fuli` 进程里跑，实测：

```
ETXRcPro: stat pollHz=60 replyHz=59 changeHz=0 skip=3 poll=121 iv=0 btn=0
```

- `pollHz=60`：我们发请求的频率
- `replyHz=59`：**服务端真的回了 59 次/秒**
- `changeHz=0`：**值一次都没变过**

连采 30 分钟，`chan=1024,1024,1024,1024,1024,1024` 一次没变。

### 2.4 cmdId 全表扫描（新增探针 `bindscan`）

为了搞清「哪个 id 能回真数据」，在 `RcProService` 里加了扫描器，逐个 id 发一次并记录回包。

**cmdSet=6 扫 0..200，有回包的只有 5 个：**

| cs | id | 回包 | 解读 |
|---|---|---|---|
| 6 | 0 | `0004 0004 0004 0004 0004 0004` | 6×1024 —— 摇杆的**占位应答** |
| 6 | 1 | `0004 0100 0402 0004 0300 0404 0004 0500 0406` | 递增索引，像**能力枚举** |
| 6 | 3 | `00` | 1 字节 |
| 6 | 4 | `0004 0004 0004 0004 0004 0004` | **和 id=0 完全一样** ← 我们现在用的就是这个 |
| 6 | 166 | `01` | 单字节标志 |
| 6 | 173 | `0000` | 2 字节零 |

**cmdSet 0..8 各扫 id=0..12：所有 cmdSet 的 id=0 都回同一串 `0004×6`。**

这说明 id=0 是「读摇杆」的通用入口，但**固件对它只回中点占位**，
真实采样必须靠**订阅推送**（也就是 40007 那条路），不是轮询能问出来的。

**特别说明**：`cmdId=174`（我们用来拉旁键的那个）在 binder 上**完全没回包**（`waited=none`）。
之前 `docs/19` 里写的「174 轮询已建立」只是 `transact(4)` 返回了 true，
不等于服务端真的回了数据 —— 这一条现在要更正。

## 三、那别人的 22Hz 是怎么来的？

我判断有三种可能，按可信度排序：

1. **在 10Hz 真值上做插值**（最可能）。
   我们自己的 `StickSmooth` 就是这么做的：10Hz 源 → 100Hz 输出。
   别人说"22Hz"，可能指输出帧率，不是采样率。
2. **用了某条我们还没找到的订阅式 binder 推送**。
   `transact(4)` 只是「注册回调 + 发请求」，服务端真正推数据是走 `IPackListener`。
   我们现在每次 `transact(4)` 都重新注册一次回调（60Hz），
   **这可能反而让服务端不停地重置订阅**，导致它永远只回初始占位值。
   → **下一步该试的是：只注册一次回调，然后什么都不做，看服务端会不会自己推。**
3. **接了外部硬件**（ESP32 读 MCU 串口）。这跟软件路径无关。

第 2 条是我目前最想验的假说，因为它能同时解释「60Hz 有回包但值不变」和「40007 拿不到订阅」。

## 四、按键与拨轮：现在到底能拿到什么

### 4.1 拨轮切档（已实现）

`40007` 的 `06/AE` 帧，载荷偏移 16 开始的 6 个 u16：

```
off=16: RH  off=18: RV  off=20: LV  off=22: LH  off=24: 左波轮  off=26: 右波轮
```

我们已经在读 `raw[4]`/`raw[5]`，代码在 `DumlStick.java` 与 `Radio.applyRcProButtons()`。
**这部分不需要再找，是通的。** 你抱怨的"拨杆没适配"，根因在 `docs/18` 里分析过：
是 `ch4/ch5` 到底该映射到 P1/P2 还是独立 K1/K2 的语义问题，不是数据拿不到。

### 4.2 后面两个自定义键 / 前面拍照录像键

按参照实现（`RCPro-资料/d3`）的说法，这些在 `06/174` 帧的 `p0/p1/p2` 位域里：

| 字节 | 位 | 含义 |
|---|---|---|
| p0 | 0x01 / 0x02 / 0x04 | 快门 / 录像 / 返航（**待确认**） |
| p1 | 0x80 等 | 五维拨杆方向 |
| p2 | 0x04 / 0x08 / 0x10 | C1 / C2 / C3 |

**但本机实测：`40007` 从头到尾没出现过 `06/174` 带非零 p0 的帧。**
测了 3000+ 帧，`06/174` 只出现过 1 次，载荷 14 字节，`p0=0x00`。

也就是说：**这台机器上，按键根本没有从 40007 出来过。**
要么是这些键的事件走另一条路（evdev？binder？），要么需要先"进入某个模式"才开始上报。

这一点我还没查到答案，是下一个要攻的点。

### 4.3 物理按键（evdev）—— 已确认没有

```
$ getevent -pl
add device 1: qpnp_pon        KEY_VOLUMEDOWN, KEY_POWER
add device 2: gpio-keys       KEY_VOLUMEUP
add device 3: himax-touchscreen  KEY_HOME/POWER/MENU/BACK/SEARCH/BT_TOUCH/APPSELECT
```

**整机只有 3 个输入设备，没有任何摇杆/按键矩阵设备。**
`gpio-keys` 只有一个音量上键。所以「用无障碍服务收物理键」这条路在 RC2 上基本没有可用键位
（RC Plus 2 上才有意义，那台的 `gpio-keys` 键表不一样）。

## 五、下一步（按优先级）

1. **试「只注册一次回调，不重复 transact」** —— 验证 §3 第 2 条假说。
   改法：`transact(4)` 只发一次，之后静默 30 秒，看 `IPackListener` 会不会自己连续回调。
   如果会 → 我们一直在自己打断订阅，改掉就能拿到真值推送（且可能是 60Hz 级别的）。
2. **找 `40007` 的「重新订阅」动作** —— force-stop 后 40007 会彻底哑掉，需要某个 binder/DUML 调用唤醒。
   找到它，等于解决了「每 3~6 秒 RST」的历史顽疾。
3. **按键普查** —— 在 40007 / binder 全静默时，按住物理键观察是否有新帧型出现；
   必要时用 `dumpsys input` / `getevent -t` 全程录。
4. 若以上都不成，考虑硬件路线（ESP32 直读 MCU UART），这在 `lab/` 里有既有固件。

## 六、本轮新增的调试钩子（已进 1.48.0）

```bash
# 扫描 cmdSet=6 下 id 0..200，看哪些 id 有回包
adb shell am start -n com.rc2.etx/.MainActivity \
  --es action bindscan --ei cs 6 --ei from 0 --ei to 200

# 对单个 id 连发 n 次，打印完整回包（16 进制）
adb shell am start -n com.rc2.etx/.MainActivity \
  --es action bindraw --ei cs 6 --ei id 4 --ei n 8
```
