# 22 · 「别人 22Hz」之谜 —— 结论

> 承接 `21-高频通路与按键普查-20261106.md`。
> 本篇只回答一个问题：**能不能拿到比 10Hz 更快的真摇杆？**

---

## 一、结论

**不能。10Hz 就是这台机器摇杆数据的上限。**

我用「DUML 序号连续性」把这件事证死了，不是推测：

```
ETX-Duml: stat hz=23 stickHz=9  stick=79  frames=190 bad=0 gap150=1 seq=518 lost=0 gapN=0
ETX-Duml: stat hz=23 stickHz=10 stick=89  frames=213 bad=0 gap150=1 seq=518 lost=0 gapN=0
ETX-Duml: stat hz=22 stickHz=8  stick=98  frames=236 bad=0 gap150=1 seq=518 lost=0 gapN=0
ETX-Duml: stat hz=25 stickHz=10 stick=108 frames=261 bad=0 gap150=1 seq=518 lost=0 gapN=0
```

- `lost=0`：**累计跳号量 0** —— 服务端发的每一帧我们都收到了
- `gapN=0`：**从未发生过跳号**
- `bad=0`：没有一帧 CRC 校验失败
- `stickHz=9~10`：摇杆帧就是 9~10 帧/秒

**如果源是 22Hz 而我们只收到 10Hz，那么 `lost` 会以每秒 12 的速度增长。它一直是 0。**

> 注：`seq` 一直显示 518，是因为固件对同一批推送复用同一个序号（不是逐帧自增）。
> 这本身也是个证据：**它压根没打算按帧序号节奏推** —— 有变化才推。

---

## 二、那别人的「22Hz」到底是什么

一句话：**跟我们做的插值是一回事，不是采样率。**

我们的摇杆链已经是 **10Hz 源 → 100Hz 输出**：

- `StickSmooth` 在两帧真值之间做线性插值（窗口 60ms，**不外推**）
- 控制环 `CTRL_MS=10`（100Hz）
- 推流环 `PUSH_MS=4`（250Hz）

PC 端实测过：`hz=9.56`（源）、`push_hz=226~229`（推给 ViGEm）。**这已经是 24 倍插值。**

别人说的 "22Hz"，从数字上很像：
- 要么是把 10Hz 源做成 22Hz 输出的插值系数
- 要么是另一条低频通路（比如 binder 60Hz 空转，人家只取有效变化的那部分）

**但无论哪种，都没有改变 10Hz 这个源头。** 插值能救手感，救不了延迟——
物理上，你推杆到画面响应，最少要等 1/10 秒才拿到第一个真值点。

---

## 三、为什么这台机器只有 10Hz

`dji_link` 对本地客户端做了明确限制：

1. **同样的数在 40009 上也一样**：独占 30 秒收 10 帧（0.33Hz 甚至更慢），且全是 1024 占位
2. **binder 60Hz 是空转**：`replyHz=59` 但 `changeHz=0`，连采 30 分钟一次没变
3. **只注册一次回调后它根本不推**：实测 30 秒内只回最初 3 次，之后完全静默

三条路都指向同一个事实：**真值只在 40007 上，由固件按 ~10Hz 主动推，问不出来也逼不出来。**

---

## 四、对用户那两个诉求的诚实回答

| 你要的 | 能不能做到 | 说明 |
|---|---|---|
| 摇杆高频接收 | ❌ **不可能超过 10Hz** | 源头限制。但手感已经用 100Hz 插值优化过了 |
| 切档（后面两个自定义键） | ⚠️ **拨轮可以，自定义键还没找到** | 拨轮 = `06/AE` 的 `raw[4]/raw[5]`，已实现。自定义键在 40007 上从未出现过 |
| 前面拍照 / 录像键 | ⚠️ **未确认** | 按参照实现应在 `06/174` 的 p0 位域，但本机 3000+ 帧里 `06/174` 只出现 1 次且 p0=0 |

## 四之补：现有平滑实现已经是对的

查了 `StickSmooth.value()`（`app/src/com/rc2/etx/radio/StickSmooth.java:230-267`），
当前做法**正是正确的那种**：

```java
float win = (tLast <= tPrev) ? 1f : (float)(tLast - tPrev);
if (win > 45f) win = 45f;     // 窗口上限 45ms
if (win < 20f) win = 20f;     // 下限 20ms
float u = (nowMs - tLast) / win;   // u 夹在 [0,1]
out = yPrev + (yLast - yPrev) * u; // 帧间线性插值
```

- **只插值，不外推** —— `u` 上限是 1，永远停在最新真值上，不会越过
- 窗口 45ms 而不是整段 100ms —— 避免"晚一帧"的滞后感
- 档位 `LVL_CAP/LEVEL` 只控制低通混合比例，不改插值框架

所以「10Hz 源 → 100Hz/250Hz 输出」这条路我们已经在走了，
**不需要重写，只需要调参**（`smoothLevel` 当前 = 2）。

## 五、下一步真正值得做的

既然频率上限定死了，**唯一能改善手感的方向是降低延迟，不是提高频率**：

1. **把插值窗口从 60ms 压到 20~30ms**
   现在 `WIN=60ms` 是为了在 10Hz 下掩盖抖动。压小会更跟手，但抖动更明显。这个可以做成可调，让用户自己选。
2. **预测补偿**（有风险）
   在插值基础上加一点点速度外推。`StickSmooth` 之前试过外推，结果是"冲出再回拉"（单拍跳变 539），
   所以当前版本**故意不做外推**。要加只能加非常小的量。
3. **找 `40007` 的订阅唤醒动作** —— 这才是唯一有可能突破 10Hz 的地方。
   force-stop 后 40007 会彻底哑掉，说明存在一个"重新订阅"的动作我们没找到。
   如果能找到，并且它支持更高频率的推送模式，那才是真正的突破。

| 1.48.3 | 修正 seq 偏移（载荷 `[4..5]`，原来错写成 `[6..7]`） |

### ⚠️ 顺带修的一个大坑：`versionCode` 计算错误

`build-apk.ps1` 原来把版本号里所有数字直接拼起来当 versionCode：

```
1.46.44  →  14644
1.48.0   →   1480     ← 比 14644 小！
```

于是 `adb install` 报 `INSTALL_FAILED_VERSION_DOWNGRADE`，
而 adb 的这条失败信息夹在长输出里很容易看漏 —— **设备上跑的其实一直还是 1.46.44**。

我为此白查了近两小时：代码明明改了，logcat 里却一行新日志都没有，
一度怀疑是 `onNewIntent` 没触发、线程没起来、日志被过滤……

已经修成 `主*10000 + 次*100 + 修订`：

```
1.46.44  →  14644
1.48.0   →  14800
```

**教训**：以后改完代码，第一件事是 `dumpsys package <pkg> | grep versionName`
确认装上去的到底是哪一版。光看 `install` 返回值不够。

## 七、可供复现的命令

```bash
# 看真实丢帧率（关键指标：lost 应该一直为 0）
adb logcat -s ETX-Duml | grep "stat hz"

# 扫描某个 cmdSet 下哪些 cmdId 有回包
adb shell am start -n com.rc2.etx/.MainActivity \
  --es action bindscan --ei cs 6 --ei from 0 --ei to 200

# 验证「只注册一次回调，服务端会不会主动推」
adb shell am start -n com.rc2.etx/.MainActivity \
  --es action bindlisten --ei cs 6 --ei id 4 --ei sec 30
```
