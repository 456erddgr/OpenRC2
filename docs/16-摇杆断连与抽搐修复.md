# 摇杆"老是断连 + 同时动几下就抽搐"——根因与修复

用户 2026-11-01 反馈（原话）："遥感老是断连同时动几下之后就会抽搐这个连接方式你这个有点问题"。

## 一、三个独立的缺陷

### 1. 断连：dji_link 会 RST"时钟不同源"的客户端
`dji_link` 的 40007 服务端与客户端之间有一条 12 字节心跳：

```
01 01 08 0a | X(4B BE) | Y(4B BE)
```

抓包证据（`re/simlong.pcap` 大疆模拟器 70s、`re/long.pcap` 我们的 App、`re/now.pcap` 12s）：
- 服务端 → 客户端：`01 01 08 0a | S_now | S_prev`（S 是服务端自己的时钟，两字段同源）
- 客户端 → 服务端：`01 01 08 0a | C_now | S_last`（第二个字段**回显服务端最近一次的 A**）

之前我们的三种发法都被服务端掐掉：
| 版本 | 发的内容 | 结果 |
|---|---|---|
| 不发心跳 | — | 空闲约 18~25s 后 `read` 返回 -1 |
| `(本地毫秒, 本地毫秒)` | 与服务端时钟差 3.5M | 25s 左右 `Connection reset` |
| `(本地毫秒, 服务端上一拍的本地毫秒)` | 两字段不同源 | 约 25s `Connection reset` |

**修法（1.8.9）**：收到服务端第一个心跳时记下 `srvLastA` 与墙钟时刻，之后每 30ms 发
`X = srvLastA + 经过的墙钟毫秒`，`Y = srvLastA`（回显服务端最近一拍）。
**收到服务端心跳之前一个字节都不发**（宁可静默也不要发错时钟）。

### 2. 抽搐：摇杆快照被撕裂
`handleFrame` 原来逐个写 `raw[0..5]`，而 100Hz 控制环在另一个线程读同一数组 →
读到"一半新一半旧"的值 → 多轴同时动时抽搐。

**修法（1.8.0）**：`raw` 改为 `volatile int[]`，每帧解析出**新的**数组再整体替换（一次引用发布 = 原子发布）；
新增 `copyRaw(int[])` 与 `units(float[])`，控制环和 UI 都只读一次 volatile 引用，保证 6 轴同帧。

### 3. 旧的重连逻辑自己打架
- `Radio` 看门狗有一套退避（4s/8s/16s/30s），socket 层另有一套（1s）——两套同时生效。
- `DumlStick.restart()` **另起线程**跑 `loop()`，旧线程的 `finally` 会 `close()` 掉**新** socket → 断连。

**修法（1.8.0）**：
- 重连只由 socket 层单线程负责（退避 1s/2s/4s/8s），`Radio` 看门狗降级为"每 2s 提示一次"。
- `restart()` 不再另起线程；改用 `gen` 代号：每次重启 `gen++`，旧线程发现代号变了就退出，
  并且 `finally` 里**只关自己那条 socket**（`if (sock == s)`）。

### 4. 附带修掉的两处
- **帧校验**：现在每帧必须过 CRC8(init 0x77) + CRC16(init 0x3692) 才算有效；以前不校验，噪声会被当成摇杆帧。
- **不再发任何请求帧**：删掉 `06/77` 回放实验（已证明会让 dji_link 主动断开连接）。

## 三、教训
1. **服务端会掐"时钟不同源"的客户端**——这类私有协议不能"自己编个心跳糊弄过去"，
   必须先抓真客户端（这里是大疆模拟器）比对两个方向。
2. **多线程共享可变数组要整体替换**，不要逐元素写。
3. **重连逻辑只能有一套**；两个退避 + 旧线程误关新 socket = 断连。
4. 连接数/断连率这类结论必须**跑够时间**再看（1 分钟看不出 25s 周期的超时）。
